# Exploratory usability test: lessons 001–002

**Date:** 2026-08-21

## Scope

Tested the browser-led tutorial as a new learner in Chromium through completion of lessons 001 and
002. The test created the lesson-002 prompt and harness in an isolated worktree, ran the doer,
reviewed its calculator diff, and ran the specified tests and quality check. It also deliberately
reported the prompt complete before creating it to exercise recovery. The isolated worktree and
server were removed after the test.

This was not keyboard-only, screen-reader, or visible-browser testing.

## Overall assessment

The teaching flow is clear and concrete. Lesson 001 is particularly effective at explaining the
harness, job, headless execution, and read-only boundary. Lesson 002 makes the doer's boundary and
the need for an independent check clear. The principal usability problem is that the transcript
leaves obsolete choices active, which can send a learner into an avoidable dead end.

## Findings

### High priority — resolved choices remain clickable

Earlier choice buttons remain enabled after a learner has progressed. After recovering from a
missing `factory/refactor.md`, clicking the still-visible original “I've made this step” button
produced “That choice is no longer available.”

The recovery message asked the learner to say when the file was saved, but did not offer a new
confirmation button. The learner had to infer that the coach-message box was now the valid route.

**Impact:** A routine correction can make the learner choose between many visible controls without
knowing which one is live. Choosing a plausible old control produces an error rather than helping
them continue.

**Recommendation:** Keep completed choices in the transcript, but disable them as soon as the
corresponding `choice-resolved` event arrives. Show the selected option on the completed card so
learners can distinguish history from the current prompt.

Implementation plan: [disable resolved choices](../superpowers/plans/2026-08-21-disable-resolved-choices.md).

### Medium priority — recovery leads with a raw filesystem error

The missing-file path first showed `ENOENT` and the complete worktree path. The subsequent
plain-language diagnosis was useful: it named the expected path, confirmed that `factory/` was
empty, and suggested checking the file name and save state.

**Recommendation:** Put the learner-facing explanation first, and make the raw error detail
expandable or secondary.

### Medium priority — completed history is visually noisy

Every prior lesson step and its controls remains in the page. By the end of lesson 002, it takes
attention to find the current task.

**Recommendation:** Preserve the transcript, but make completed steps visually quieter and clearly
mark the active prompt.

### Low priority — the manual quality command has an expected non-zero exit

`(cd calculator && node scripts/quality.mjs)` reports findings and exits with status 1. The lesson
explains that findings are not a broken script, but a novice may still interpret the exit status as
a failed lesson check.

**Recommendation:** State beside the manual command that a non-zero exit is expected while findings
remain, or provide an explicitly inspection-only form using `|| true`.

Implementation plan: [remaining tutorial usability improvements](../superpowers/plans/2026-08-21-remaining-tutorial-usability.md).

## Strengths

- The start choices and lesson-001 progression are easy to understand.
- Commands explain both the action and the mechanism.
- Lesson 002 makes the doer's file-only boundary and independent verification tangible.
- The tutor successfully checked both learner-created files and guided a real doer run.
- The recovery diagnosis was substantively helpful once the learner reached it.
