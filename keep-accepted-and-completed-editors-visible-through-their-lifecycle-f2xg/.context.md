## Problem

A seeded editor can be accepted automatically while the learner is still reading it. Acceptance and completion are separate workbook events, but the browser currently treats acceptance as the end of the editor lifecycle. The editor becomes non-editable and then disappears before the learner completes the block. After completion, only a success message remains; the accepted source text is no longer visible.

The play-test evidence is in:

`tutorial/.tutorial/session-20260831-235044-0fb879a5/workbook/events.jsonl`

For `lesson--tetris--read-the-spec`, `attempt_accepted` and `work_accepted` were written at 06:51:12, while `block_completed` was not written until 06:53:11. The editor therefore disappeared during a real two-minute accepted-but-incomplete interval.

## Root cause

The server and browser collapse two distinct concepts:

- `tutorial-engine/src/workbook/workflow.ts` projects an active accepted editor as `editorStatus: "unlocked"`.
- `tutorial-engine/web-workbook/src/workbook-ui.tsx` treats `"unlocked"` as completed, excludes accepted checkpoints from editability, and only renders the editor surface while it can edit.
- `tutorial-engine/web-workbook/src/activity-band.tsx` removes accepted editors from the live activity band.
- Existing UI tests explicitly expect accepted and completed editor surfaces to be absent, so the deterministic suite protects the defect.

## Required learner experience

The editor lifecycle must have four distinct presentation states:

1. **Editing or reviewing:** the editor is visible in the sticky activity band and remains editable.
2. **Accepted but incomplete:** the accepted feedback and Continue control appear, but the same editor remains visible, sticky, and editable.
3. **Edited after acceptance:** the new revision enters the ordinary quiet-period review lifecycle. Continue becomes ineligible until the newest revision is accepted again. The already-revealed successor may remain visible; authored material must never be retracted.
4. **Completed:** the editor leaves the sticky activity band but remains visible beneath its authored timeline record as read-only history, showing the accepted revision that was completed.

Acceptance makes the current revision eligible for completion; it does not complete the block or make its editor historical. Completion is the sole transition to read-only presentation.

Terminal and reflection lifecycle semantics must not change.

## State and durability rules

- Give active accepted editors a state distinct from completed/unlocked editors.
- Permit only editor evidence to supersede an accepted attempt while that editor block remains active.
- A post-acceptance edit invalidates completion eligibility until the new current attempt is accepted. Keep the durable `work_accepted` event and the already-rendered successor; use the current editor attempt to decide completion eligibility.
- Complete only a currently accepted editor revision. This guarantees that completed history and the promoted workspace file describe the same accepted text.
- Project the completed editor's accepted text from durable attempt state after completion and restart.
- Do not permit new submissions after completion.
- Preserve monotonic revisions, stale-response rejection, focus/cursor stability, local draft preservation, debounce behavior, and fatal-state protections.

## Rendering rules

- Separate `visible`, `editable`, `active/sticky`, and `completed` instead of deriving them from one boolean.
- Accepted success feedback remains welded beneath the editable editor.
- Completed success feedback remains associated with the read-only editor.
- Render completed editor history beneath the authored timeline record, analogous to accepted terminal history, but use a read-only editor surface rather than a plain message.
- The completed historical editor must not autofocus, accept input, schedule review, register pending local revisions, or appear in `.current-activity-band`.
- Avoid duplicate editor surfaces during the activity-band-to-history handoff.
- Keep one Continue control for an accepted active block.

## Tests-first implementation

Replace the tests that encode the defect and add coverage at three boundaries:

### Attempt store and workflow

- An accepted editor attempt may be superseded by a higher editor revision.
- Accepted terminal and reflection attempts remain protected.
- Accepted active editor state is `active: true`, `completed: false`, includes `draftText`, and is completion-eligible.
- Editing after acceptance creates a reviewing current revision and makes completion ineligible.
- Re-acceptance restores eligibility.
- Completion projects an inactive, completed, read-only editor with the same accepted text.
- Restart reconstructs that completed editor history.

### Browser component lifecycle

- Accepted active editor remains in the activity band and `contenteditable="true"`.
- Acceptance does not replace the CodeMirror instance, lose focus/cursor, drop local text, or cancel a legitimate pending newer revision.
- A post-acceptance edit follows the existing debounce/review path.
- Completion removes the sticky band and renders one historical editor with `contenteditable="false"`.
- Completion cancels pending submissions and historical rendering cannot submit.
- Accepted and completed success feedback appear once.

### Regression and visual coverage

- Terminal acceptance/history behavior remains unchanged.
- Fatal-state read-only behavior and stale/out-of-order editor response guards still pass.
- Update the visual affordance gallery and received screenshots for accepted-live and completed-history editor states where needed.
