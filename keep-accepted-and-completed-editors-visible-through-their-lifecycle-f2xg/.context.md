## Problem

Practice acceptance and block completion are separate workbook events, but both live practice surfaces currently treat acceptance as the end of their lifecycle.

- A seeded editor can be accepted automatically while the learner is still reading it. The editor becomes non-editable and disappears before the learner completes the block. After completion, only a success message remains; the accepted source text is no longer visible.
- An accepted terminal immediately leaves the sticky activity band and is replaced by frozen history even though its block remains active. The learner loses the shell before choosing to complete the block.

The editor play-test evidence is in:

`tutorial/.tutorial/session-20260831-235044-0fb879a5/workbook/events.jsonl`

For `lesson--tetris--read-the-spec`, `attempt_accepted` and `work_accepted` were written at 06:51:12, while `block_completed` was not written until 06:53:11. The editor disappeared during a real two-minute accepted-but-incomplete interval. The existing terminal component and UI tests confirm the same accepted-before-completed handoff for terminal practice.

## Root cause

The server and browser collapse accepted work and completed history:

### Editor

- `tutorial-engine/src/workbook/workflow.ts` projects an active accepted editor as `editorStatus: "unlocked"`.
- `tutorial-engine/web-workbook/src/workbook-ui.tsx` treats `"unlocked"` as completed, excludes accepted checkpoints from editability, and only renders the editor surface while it can edit.
- `tutorial-engine/web-workbook/src/activity-band.tsx` removes accepted editors from the live activity band.

### Terminal

- The terminal lifecycle uses `phase: "complete"` for accepted evidence even while the workbook block remains incomplete.
- `TerminalBlock` hides the live xterm when that phase appears.
- `practiceSurfaceSource` and `ActivityBand` remove a terminal with accepted evidence from the live activity band and show its frozen snapshot as history.
- `terminalJobIsCurrent` rejects every later review once any `work_accepted` exists for the block, so merely keeping the terminal interactive would create commands that cannot be accepted.

Existing tests explicitly expect accepted editor and terminal activity bands to be absent, so the deterministic suite protects the defect.

## Required learner experience

Editor and terminal practice share one lifecycle contract:

1. **Working or reviewing:** the practice surface is visible in the sticky activity band and remains interactive.
2. **Accepted but incomplete:** accepted feedback and Continue appear, but the same editor/xterm remains visible, sticky, and interactive.
3. **Changed after acceptance:** an editor revision or terminal command becomes the current attempt and follows the ordinary review lifecycle. Continue becomes ineligible until that newest attempt is accepted. Already-authored successor material remains revealed; durable authored material is never retracted.
4. **Completed:** the practice surface leaves the sticky activity band but remains visible beneath its authored timeline record as read-only history. Editor history shows the accepted source text; terminal history shows the accepted transcript snapshot.

Acceptance makes the current evidence eligible for completion. It does not complete the block, release the live surface, or make that surface historical. Explicit block completion is the sole transition to read-only history.

Reflection presentation is outside this change and must not regress.

## State and durability rules

- Give active accepted editor and terminal attempts states distinct from block completion.
- Permit an accepted editor attempt to be superseded while its editor block remains active.
- Permit a later terminal command to become the current terminal attempt and receive review while its terminal block remains active.
- A post-acceptance change invalidates completion eligibility until the new current attempt is accepted. Keep the durable `work_accepted` event and already-rendered successor, but decide `canComplete` from current attempt acceptance for evaluated practice blocks.
- Complete only a currently accepted practice attempt. This guarantees that completed history corresponds to evidence that was accepted.
- Project completed editor text and terminal snapshot from durable accepted evidence after completion and restart.
- Do not permit editor submissions or interactive terminal input after completion.
- Preserve monotonic editor revisions, terminal attempt identity, stale-response rejection, focus/cursor stability, local editor draft preservation, xterm/WebSocket identity, debounce behavior, and fatal-state protections.
- A stale editor review or terminal review may not restore eligibility, overwrite newer evidence, or replace the current practice state.
- Repeated acceptance must not duplicate `work_accepted` or authored successor records.

## Rendering rules

- Separate `visible`, `interactive`, `active/sticky`, `accepted`, and `completed` instead of deriving them from one overloaded status.
- Accepted success feedback remains welded beneath the live editor or terminal.
- Accepted state must not replace the CodeMirror or xterm instance.
- Completion removes the surface from `.current-activity-band` and inserts one read-only historical surface beneath its own authored record.
- Completed editor history uses a read-only editor surface with the accepted text and success feedback.
- Completed terminal history uses the frozen accepted transcript and success feedback.
- Historical surfaces must not autofocus, accept input, schedule review, publish local revisions, register terminal insertion, or reconnect transports.
- Avoid duplicate practice surfaces during the activity-band-to-history handoff.
- Keep exactly one Continue control for an accepted current attempt.

## Tests-first implementation

Replace tests that encode the defect and add coverage at four boundaries.

### Attempt and workflow lifecycle

- An accepted editor attempt may be superseded by a higher editor revision; accepted reflection attempts remain protected.
- Accepted active editor and terminal blocks remain `active: true` and `completed: false`, retain their accepted evidence, and are completion-eligible.
- An editor edit or terminal command after acceptance becomes current and makes completion ineligible.
- The newest editor revision and terminal attempt can be reviewed and accepted; re-acceptance restores eligibility without duplicating work acceptance or authored material.
- Completion projects inactive completed read-only history with the same accepted editor text or terminal snapshot.
- Restart reconstructs accepted-active and completed-history states correctly.

### Live browser lifecycle

- Accepted editor remains in the activity band and `contenteditable="true"`.
- Accepted terminal remains the same live xterm in the activity band with stdin enabled.
- Acceptance does not replace CodeMirror/xterm identity, lose editor focus/cursor, drop local text, close/recreate the terminal WebSocket, or cancel a legitimate pending newer attempt.
- Post-acceptance changes follow existing debounce/command observation and review paths.
- Accepted success feedback and one Continue control remain visible.

### Completed browser history

- Completion removes the sticky activity band and renders exactly one historical editor/terminal surface.
- Editor history is `contenteditable="false"` and shows the completed accepted text.
- Terminal history is frozen and shows the completed accepted snapshot.
- Completion cancels pending submissions; historical surfaces cannot submit, autofocus, or reconnect.
- Accepted and completed feedback appears once.

### Regression and visual coverage

- Reflection acceptance behavior is unchanged.
- Fatal-state read-only behavior, terminal transport behavior, and stale/out-of-order editor and terminal response guards still pass.
- Update visual affordance fixtures and received screenshots for accepted-live and completed-history practice states where needed.
