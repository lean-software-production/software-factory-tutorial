Replace the tiny natural-language calculator exercise with a more ambitious, playful terminal pixel-creature generator and expand the bounded Ralph loop from two to five passes.

## Same specification, different applications

Every learner receives the same deliberately open `spec.md`. They inspect the seed in a read-only editor-style view rather than writing it from scratch. The lesson asks them to notice both the requirements and the decisions left to the factory.

Every factory receives the same specification and worker instructions. Variation comes from agent interpretation: creature shapes, terminal composition, ANSI styling, names, personality, trait descriptions, architecture, and implementation choices. A cohort should produce visibly different applications and creatures despite identical authored inputs.

Change the learning outcome from “draft a small specification” to “inspect a seed and identify where it permits variation.” Keep the worker-prompt and bounded-loop activities learner-authored.

## Five-pass shape

1. Pass 1 creates and commits a plan of exactly four similarly sized, independently testable implementation tasks, then stops.
2. Passes 2–5 each complete exactly one unchecked task, run any checks available to that worker, update `plan.md`, commit useful work, and stop.

The exact four-task decomposition may vary between factories. The invariant is one planning pass plus four meaningful work passes. The worker prompt explicitly prohibits continuing to a second task in the same pass. Verification-only/no-op work does not create empty commits.

`ralph.sh` runs exactly five bounded `pi -p < prompt.md` invocations and prints explicit, readable `Pass N/5` boundaries before each invocation. The learner can run the resulting application in the existing terminal without a preview server. Omit `--no-session`: session-storage semantics are not needed to understand this bounded loop and may be introduced later only if a lesson depends on them.

## Creative output before shared validation

The common prose specification describes expected behaviour while leaving creative presentation open. It deliberately provides no machine-readable output contract; the inconsistency this permits helps motivate the next validation lessons. It should request enough shared behaviour to make comparison meaningful, for example:

- A stable human-facing command such as `npm start -- --seed <text>`.
- Deterministic output for the same seed within one implementation.
- Meaningfully different creatures for different seeds.
- A terminal-friendly pixel creature with traits or personality.
- Predictable help and error behaviour.
- A no-colour or otherwise accessible fallback.

Do **not** provide a trusted shared validator or contract checker in this first factory. Workers may create and run their own tests, but those checks are part of each factory’s implementation and do not standardise the cohort.

The intended evidence is divergence: identical specifications and loop structures produce creative differences, and may also produce inconsistent interpretations of requirements that looked common. Terminal block acceptance confirms that five bounded passes ran and returned; it does not certify product conformance.

The workbook does not compare cohort outputs, add a validation reflection, or change Part 2. In a live class, the facilitator may compare the different applications and use their inconsistencies to discuss what validation could standardise without removing creativity.

## Acceptance

- Every learner starts from the same authored specification and worker task.
- The spec is inspectable but is not an evaluated write-from-scratch exercise.
- A deterministic play-test normally produces five distinct commits/states rather than one worker completing everything.
- Different clean sessions produce visibly different terminal applications from the same specification.
- No supplied validator makes those applications falsely appear certified.
- Pass boundaries are visible in terminal evidence.
- Fresh agents coordinate only through the prompt and repository files.
- The block can accept useful partial progress; completion does not depend on a perfect final product.
- Curriculum prose follows the glossary and 100-column rule.

## Candidate shared specification

```markdown
# Pixel creature generator

Build a command-line application that creates a pixel creature from a text seed.

Run it with:

    npm start -- --seed <text>

The application prints one complete creature card in the terminal. The card contains a pixel-art
creature, a generated name, and a short list of traits. The same seed must produce the same card
within one implementation. Different seeds should normally produce different creatures.

`--help` explains the command. A missing seed produces a useful error and a non-zero exit status.

Make strong creative choices. You decide the creature anatomy, characters, colours, layout, naming
style, personality, and any extra features. Keep ordinary output readable in a standard terminal and
provide a usable no-colour fallback. Do not use the network at runtime.

Include useful automated tests, but do not build a validator for other implementations.
```

This is a candidate, not yet authored curriculum. Review it for enough fixed behaviour to make cohort
comparison meaningful and enough freedom to produce visibly different applications. Do not add a
shared validator to the seed.

- `72682cd` deterministic generation
- `f24b46c` creature-card renderer
- `4b7c366` CLI integration

The agents respected the one-task-per-pass boundary. The final project had 27 passing tests and roughly
1,400 implementation/test lines. Agent work took about 15 minutes from the plan commit to completion.
The `matt` and `donkey` seeds produced deterministic but similarly structured boxed creature cards.

Learner feedback: the result was not creative enough and did not feel fun to use. The fixed
seed/determinism/card requirements channelled the factory into deep engineering of a report-like CLI
rather than a playful experience. Keep the five-pass plan/commit mechanism, but supersede the pixel
creature product with a terminal game that leaves much more room for creative mechanics, story, art,
and interaction. Retain this workspace as evidence; do not turn it into authored curriculum.
