Replace the tiny natural-language calculator exercise with a playful terminal Tetris game and expand the bounded Ralph loop from two to five passes.

## Same familiar game, different implementations

Every learner receives the same authored `spec.md` in a read-only editor-style view. They do not write the seed from scratch. Familiar Tetris rules provide a shared reference, while agents remain free to choose architecture, controls, rendering, colours, pieces, scoring details, effects, and extra features. A cohort should produce recognisably similar games with visibly different implementations.

Change the learning outcome from “draft a small specification” to “inspect the seed that every worker will follow.” Keep the worker-prompt and bounded-loop activities learner-authored.

## Five-pass shape

1. Pass 1 creates and commits a plan of exactly four similarly sized, independently testable implementation tasks, then stops without implementing the game.
2. Passes 2–5 each complete exactly one unchecked task, run relevant checks, update `plan.md`, commit useful work, and stop.

The exact task decomposition may vary between factories. The worker prompt explicitly prohibits continuing to a second task in one pass. Verification-only/no-op work does not create empty commits.

`ralph.sh` runs exactly five bounded `pi -p < prompt.md` invocations and prints explicit `Pass N/5` boundaries. The manual prototype selects `opencode/gemini-3-flash:low` directly so the five-pass play-test uses a fast model without extra configuration. Omit `--no-session`: session-storage semantics are not needed for this lesson.

Git is available through completed Yak `provision-git-for-factory-workers-bqnf`; every useful pass commits to the session-local live workspace repository.

## No shared validation yet

Do not provide a trusted validator or contract checker. Workers may create and run tests, but those checks belong to each implementation. Terminal block acceptance confirms that five bounded passes ran and returned; it does not certify rule conformance or game quality.

The workbook does not compare cohort outputs or alter Part 2. In a live class, the facilitator can let learners play and compare the games, then discuss what a shared validator could standardise without removing creative choices.

## Acceptance

- Every learner starts from the same authored specification and worker task.
- The spec is inspectable but is not an evaluated write-from-scratch exercise.
- A play-test normally produces one plan commit and four distinct implementation commits.
- Workers stop after one task per pass.
- Different clean sessions produce recognisably correct but visibly different terminal games.
- The game is playable in the workbook terminal and restores terminal state on exit.
- No supplied validator makes the result falsely appear certified.
- Pass boundaries are visible in terminal evidence.
- The block can accept useful partial progress; it does not depend on a perfect final game.
- Curriculum prose follows the glossary and 100-column rule.
