Replace the tiny natural-language calculator exercise with a more ambitious, playful terminal pixel-creature generator and expand the bounded Ralph loop from two to five passes.

## Same seed specification, different applications

Every learner receives the same deliberately open `spec.md`. They inspect the seed in a read-only editor-style view rather than writing it from scratch. The lesson should ask them to notice both the fixed contract and the decisions left to the factory.

Every factory receives the same specification and worker instructions. Variation should come from agent interpretation: creature shapes, terminal composition, ANSI styling, names, personality, trait descriptions, and implementation choices. A cohort should produce visibly different applications and creatures despite identical authored inputs.

Change the learning outcome from “draft a small specification” to “inspect a seed and identify where it permits variation.” Keep the worker-prompt and bounded-loop activities learner-authored.

## Five-pass shape

1. Pass 1 creates and commits a plan of exactly four similarly sized, independently testable implementation tasks, then stops.
2. Passes 2–5 each complete exactly one unchecked task, run relevant checks, update `plan.md`, commit useful work, and stop.

The exact four-task decomposition may vary between factories. The invariant is one planning pass plus four meaningful work passes. The worker prompt must explicitly prohibit continuing to a second task in the same pass. Verification-only/no-op work must not create empty commits.

`ralph.sh` runs exactly five bounded `pi --no-session -p < prompt.md` invocations and prints explicit, readable `Pass N/5` boundaries before each invocation. The learner should be able to run the resulting app in the existing terminal without a preview server.

## Creative output with a standard contract

Standardise the interface and machine-readable contract, not the creative presentation. The shared specification and supplied contract checker should require at least:

- A stable command such as `npm start -- --seed <text>` for the creative human-facing terminal output.
- A machine-readable mode such as `--format json` with a documented common schema.
- Deterministic output for the same seed within one implementation.
- Meaningfully different creatures for different seeds.
- A fixed logical pixel-grid size represented in the JSON contract.
- Valid trait metadata and predictable exit/error behaviour.
- A no-colour or otherwise accessible fallback for terminal output.
- Automated contract checks that any conforming implementation can run.

The default terminal experience remains open to interpretation: agents may make different choices about ANSI palettes, borders, layout, creature anatomy, names, lore, and other presentation. The JSON mode gives validation and downstream tools something dependable to consume without forcing the human output to look the same.

The pedagogical payoff should be explicit: **validation does not make creative outputs identical; it makes varied outputs dependable and interoperable.** Learners should compare results and discuss what the common specification and validator did—and did not—control.

## Acceptance

- Every learner starts from the same authored specification and worker task.
- The spec is inspectable but is not an evaluated write-from-scratch exercise.
- A deterministic play-test normally produces five distinct commits/states rather than one worker completing everything.
- Different clean sessions produce visibly different terminal applications while satisfying the same contract checker.
- Human-facing output has substantial creative freedom; JSON/CLI behaviour is interoperable.
- Pass boundaries are visible in terminal evidence.
- Fresh agents coordinate only through the prompt and repository files.
- The block can still accept useful partial progress if a task fails; completion does not falsely depend on a perfect final product.
- Curriculum prose follows the glossary and 100-column rule.
