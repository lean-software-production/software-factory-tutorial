## Goal

Prevent completion from committing stale accepted evidence while an accepted live editor or terminal has newer local work in flight.

## Problem

Keeping accepted practice surfaces interactive until completion exposes races hidden by the old immediate freeze.

### Editor debounce gap

An accepted editor remains eligible while the learner types a new revision. The browser now hides Continue immediately, but the draft is not authoritative until the 750 ms quiet-period POST creates a newer attempt. A tutor-triggered completion or another stale browser request could still complete the prior accepted revision during that gap.

### Terminal Enter-to-observation gap

A learner can press Enter after terminal acceptance before Bash emits the command-submitted observation. Continue, deliberate scroll, or the Tutor tool could complete the earlier accepted attempt while the new command is already starting.

### Slow departure-summary gap

`completeBlock` may run block, lesson, or workbook summarisation before writing `block_completed`. If practice input remains enabled, new work can begin during that model call, queue behind the completion transaction, then be discarded after the block advances and the editor/PTY becomes historical.

## Required behavior

- Local editor changes and terminal Enter input immediately suppress browser continuation before server acknowledgement.
- The server has an authoritative per-block completion fence shared by Continue, scroll completion, and Tutor-tool completion.
- Completion establishes the fence only after confirming the current attempt is accepted, but before any departure summarisation.
- Once fenced, the editor endpoint rejects new revisions and the terminal manager rejects new command-entering input/observations for that block.
- Work already started before the fence must invalidate/reject completion rather than be lost.
- Keep the live editor/PTY mounted until `block_completed` is durable; then perform the existing history/transport handoff.
- If completion is rejected, generation changes, or summarisation fails without completing, release the fence safely. Fatal summarisation failure may leave the whole workbook disabled under the existing fatal contract.
- Do not add arbitrary delays. Tests use deferred promises/observable callbacks.

## Architecture seam

Introduce a small workflow/terminal-manager handshake rather than inferring from DOM state:

- Terminal manager tracks command-entering input synchronously and can report/fence a block before shell protocol observation catches up.
- Workflow can ask whether local terminal command input is pending and can begin/end a terminal completion fence through dependency callbacks.
- Editor draft submission checks the same workflow completion-fence state.
- Browser tracks expected editor/terminal revisions to hide continuation immediately, but server checks remain the correctness boundary.

Keep the interface narrow and block-scoped. Do not redesign terminal transport or persist ephemeral fence state.

## Tests

Use deterministic deferred summarisation and fake PTY/WebSocket seams to cover:

- accepted editor local edit immediately hides Continue;
- editor POST arriving before completion invalidates completion;
- editor POST arriving after completion fence is rejected and not lost silently;
- accepted terminal Enter immediately hides Continue;
- pending terminal command before completion request rejects completion;
- terminal input after the fence is rejected/ignored before reaching PTY or observation;
- completion from button/API, scroll-equivalent API, and Tutor tool shares the same server fence;
- slow summarisation cannot race new practice work;
- rejected completion releases the fence where continuation remains possible;
- no command/draft is silently discarded.

## Tutor-request product decision

A Tutor message may reply normally or invoke completion. If an accepted practice surface remains editable while that request is in flight, the learner can create local work after the request captured its expected revision but before the Tutor calls completion.

The smallest strict fence temporarily disables practice input for a completion-capable Tutor request while keeping the surface visible. That guarantees no unseen edits, but briefly makes accepted practice read-only before completion. Keeping it editable requires a larger browser/server dirty-work lease protocol. Leaving it editable without that protocol accepts a narrow stale-completion race.
