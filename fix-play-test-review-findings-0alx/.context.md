## Finding 1: successful terminal work became a completion trap

The first `bash ralph.sh` attempt (events 106–109) exited 0 and contained two distinct Pi outputs. The Practice Coach handoff said the evidence was ready and explicitly recognised both passes. The subsequent Main Tutor review failed and displayed “Review is temporarily unavailable. Please run the command again in a moment.”

The learner then explored the generated calculator. Terminal feedback repeatedly insisted on another `bash ralph.sh`, despite the original successful evidence. Main Tutor chat contradicted itself:

- It said the transcript showed `bash ralph.sh` ran two passes and returned to the prompt.
- It then demanded another run because pass markers were not visible.
- The script itself did not print explicit pass markers.
- The later accepted rerun also lacked those explicit markers.

The system made an infrastructure failure look like learner failure and required repetition of successful work.

The full terminal transcript already exists server-side, but automatic Main Tutor review was explicitly denied terminal context. The Tutor also lacked tools to inspect workspace state. These evidence boundaries likely caused the contradictory judgment, although transient review failure also needs independent recovery.

Expected outcome: completed evidence remains authoritative; transient failure retries assessment against the same evidence; the Main Tutor can inspect the transcript and workspace before deciding; no learner command rerun is required.

## Finding 2: Practice Coach creates inconsistent architecture

Editor practice is reviewed directly by the Main Tutor, while terminal practice uses a terminal-only Practice Coach followed by a Main Tutor handoff for ready/interesting work. The learner experiences one Tutor, but the implementation has two model-backed roles and different review paths.

The Practice Coach may use a faster model for quick terminal feedback, but successful work takes a sequential Coach-then-Tutor path and introduces handoff information loss, extra failure states, configuration/preflight complexity, and terminology ambiguity. The play-test exercised this weakness.

Decision from review: remove the Practice Coach, use direct Main Tutor terminal review, and measure latency before adding any faster route. If measured latency is unacceptable, create a follow-up decision rather than preserving speculative complexity.

## Finding 3: editor feedback/loading state was unstable

The learner observed visible glitching in the editor feedback bar. More importantly, a generic loading/reviewing status replaced useful feedback that the learner was actively following.

The bottom-bar editor messages were produced by the Main Tutor, even though their in-place presentation made them feel like “coach feedback.” They are hidden from the public conversation timeline and projected through the editor checkpoint.

The complaint is about feedback/loading state, not repetitive Tutor wording.

Desired behaviour:

- Review only after editing has gone quiet.
- Keep the last actionable feedback visible while updating.
- Show a subtle spinner/updating indicator beside it.
- Replace feedback atomically only when the latest review completes.
- Stale/out-of-order responses cannot win.
- Failures retain useful feedback and show a non-destructive retry state.
- Preserve editor focus, cursor, and current draft.

## Finding 4: terminal/editor feedback presentation should be consistent

Terminal status and feedback should use the same wide bar attached beneath the work surface as the editor. Share width, border treatment, lower corners, spacing, typography, colour, spinner, ARIA, and reduced-motion behaviour. Avoid a separate terminal speech-bubble language. Running, reviewing, updating, actionable feedback, temporary failure, and completion should remain distinguishable without changing component geometry.

## Finding 5: Tutor explanation of `--no-session` was wrong

When asked what `--no-session` does, the Main Tutor initially claimed that without it Pi may reuse or resume its default saved session. The learner tested two separate `pi -p` invocations and demonstrated that they did not share conversational memory. The Tutor then partially corrected itself.

Pi CLI semantics from `pi --help`:

- `-p` / `--print` is a non-interactive invocation that processes a prompt and exits.
- `--continue` resumes the previous session.
- `--resume` selects a session.
- `--no-session` prevents the new invocation from being saved; it is ephemeral.

Fresh context does not depend on `--no-session`; avoiding saved-session litter does. Decide whether to correct Tutor grounding/context, make the authored lesson explanation more explicit, or both. Add a regression/eval for this natural learner question.

## Finding 6: the lesson requires a commit that the worker cannot make

The editor rubric required `prompt.md` to instruct the worker to commit useful work. Both Pi passes reported that Git was unavailable inside their execution environment. The live workspace itself is a Git repository, but its history contains only the materialisation commit; the workers created no commits.

This makes part of the required worker contract impossible. Decide deliberately between:

- Provisioning safe Git access in the worker container so commits land in the session-local workspace repository; or
- Removing/defering the commit requirement from this early lesson.

The decision must remain consistent with later lessons where the line intentionally commits to the session-local repository.

## Finding 7: the second factory pass was pedagogically weak

The first Pi pass created a broad plan, implemented the whole calculator, added tests, and got 13/13 passing. The second pass only added/completed a verification task. The learner saw repeated execution, but little meaningful incremental progress through a loop.

Consider whether the seed/prompt should constrain task size, whether the first pass should only plan or complete one deliberately small capability, or whether the lesson should explicitly say that a second pass may simply discover the work is complete. Preserve the lesson’s goal of a quick, bounded first taste rather than turning it into a production factory.
