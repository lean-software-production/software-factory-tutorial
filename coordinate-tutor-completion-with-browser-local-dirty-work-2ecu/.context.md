## Deferred edge case

An accepted practice block may be completed by the Tutor while the learner creates newer browser-local work during the same Tutor request.

Example:

1. The accepted editor/terminal remains live.
2. The learner sends a Tutor message.
3. While the Tutor model is answering, the learner types an editor change that has not reached its 750 ms submission or begins terminal input.
4. The Tutor invokes completion for the previously accepted attempt.

The current lifecycle implementation will fence authoritative submissions and terminal input once completion begins, and browser-local direct Continue/scroll is suppressed by pending revisions. The unresolved sub-debounce editor case requires either temporarily disabling practice during completion-capable Tutor requests or a browser/server dirty-work lease that lets local work veto the Tutor tool.

Matt chose on 2026-09-01 to leave this rare edge case for later rather than make practice temporarily read-only while the Tutor answers.

## Future acceptance criteria

- Keep accepted practice visible and editable during Tutor requests.
- Browser-local editor/terminal work created after request dispatch must veto stale Tutor completion before `block_completed`.
- Do not add arbitrary delays or silently discard work.
- Preserve one Main Tutor request and existing completion-tool authority.
